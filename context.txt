## 1. WHAT IS THIS PROJECT?

A production-grade full-stack email job scheduler built for the ReachInbox (Outbox Labs)
Software Development Intern Hiring Assignment.

It accepts email scheduling requests via REST APIs, queues them using BullMQ delayed
jobs (NOT cron), sends them via fake SMTP (Ethereal Email), and exposes a React
dashboard for managing everything.

## 2. ASSIGNMENT REQUIREMENTS (SUMMARY)

BACKEND (Express.js + TypeScript):
  - Accept email scheduling via API
  - Store in PostgreSQL (Prisma ORM)
  - Schedule via BullMQ delayed jobs — NO cron jobs of any kind
  - Send via Ethereal Email (fake SMTP)
  - Emails searchable via Elasticsearch
  - Live BullMQ dashboard (Bull Board)
  - Persist state: server restart = future emails still send correctly, no duplicates
  - Worker concurrency (configurable)
  - Delay between each email send (min 2s, configurable)
  - Rate limiting: global + per-sender hourly limits, Redis-backed, configurable
  - When rate limit hit: reschedule jobs to next hour (don't drop), notify via Slack
  - Slack OAuth: real OAuth flow, real webhook message on rate limit, not a log line
  - Idempotency: same email queue must NOT be sent more than once

FRONTEND (React + TypeScript + Tailwind CSS):
  - Google OAuth login (real, not mock)
  - Dashboard: user info + logout in header
  - Tabs: Scheduled Emails, Sent Emails
  - Compose New Email: subject, body, CSV upload, start time, delay, hourly limit
  - Tables with loading states, empty states
  - Clean folder structure, reusable components, proper TypeScript types

## 3. TECH STACK

Backend:
  - Language: TypeScript (strict mode)

## 6. CORE WORKFLOWS

### A) Email Scheduling Flow
  User → POST /api/emails/schedule { fromEmail, toEmail, subject, body, scheduledAt }
    → Validate input
    → Generate idempotencyKey: {userId}:{fromEmail}:{toEmail}:{timestamp}:{random8}
    → prisma.email.create(status: SCHEDULED)
    → Calculate delay: scheduledAt.getTime() - Date.now()
    → emailQueue.add('send-email', jobData, { delay, jobId: idempotencyKey })
    → Update email record with jobId
    → Index in Elasticsearch
    → Return { emailId, jobId }

### B) Bulk Scheduling Flow
  User → POST /api/emails/schedule-bulk (FormData with CSV file)
    → Parse CSV/text for email addresses (regex)
    → Deduplicate recipients
    → Generate batchId (UUID)
    → For each recipient[i]:
        scheduledAt = baseTime + (i * delayBetweenEmailsMs)
        → scheduleEmail() with staggered time
    → Return { batchId, emailCount, emailIds }

### C) Worker Processing Flow (per job)
  BullMQ fires delayed job →
    1. Load email from DB by idempotencyKey
    2. If status === SENT → skip (idempotent)
    3. checkSenderRateLimit(fromEmail) via Redis
    4. checkGlobalRateLimit() via Redis
    5. If rate limited:
       → Update status to RATE_LIMITED
       → notifyRateLimitHit() → Slack webhook (if connected)
       → rescheduleEmailJob(data, nextWindowMs + 1000)
       → Update scheduledAt in DB
       → Return (don't throw, job completes successfully)
    6. If allowed:
       → Update status to SENDING
       → await delay(DELAY_BETWEEN_EMAILS_MS) — throttle
       → incrementSenderCount() + incrementGlobalCount() (Redis INCR)
       → sendEmail() via Ethereal SMTP
       → Update status to SENT, set sentAt, etherealUrl
       → updateEmailIndex() in Elasticsearch
    7. On error:
       → Update status to FAILED, set failedAt, failureReason
       → Throw error (BullMQ retries up to 3 times with exponential backoff)

### D) Restart Recovery Flow
  Server starts → requeuePendingEmails():
    → Query DB: WHERE status IN (SCHEDULED, RATE_LIMITED) AND scheduledAt >= NOW()
    → For each email:
        delay = scheduledAt - Date.now()
        addEmailJob(data, delay)  ← jobId = idempotencyKey
    → BullMQ ignores if job already exists (same jobId = no-op)
    → Log: "Re-queued X/Y pending emails from DB"
    RESULT: No lost emails, no duplicates, correct timing preserved

### E) Rate Limiting Logic
  Redis keys per hour window:
    ratelimit:sender:{email}:{hourWindow}  → per-sender count
    ratelimit:global:{hourWindow}          → global count
  hourWindow = Math.floor(Date.now() / 3600000) — changes every clock hour
  INCR is atomic — safe across concurrent workers
  TTL = 3600s — auto-cleanup
  When limit hit:
    → Job rescheduled to: nextWindowMs = ((hourWindow+1) * 3600000) - Date.now()
    → Slack notification sent
    → Job NOT dropped or permanently failed

### F) Slack Integration Flow
  Connect:
    User clicks "Connect Slack" → GET /api/slack/connect
    → Redirect to Slack OAuth (scopes: incoming-webhook, chat:write)
    → User authorizes → Slack redirects to /api/slack/callback
    → Exchange code for token → Store slackToken + slackWebhook in User record
    → Redirect to frontend /dashboard?slack=connected
  Notification:
    Rate limit hit → notifyRateLimitHit() → sendSlackNotification()
    → Check user's slackWebhook in DB
    → If null → silently skip (no crash)
    → If present → POST to webhook URL with formatted Block Kit message
  Disconnect:
    POST /api/slack/disconnect → Set slackToken/slackWebhook/slackChannel to null

## 10. KEY DESIGN DECISIONS & TRADE-OFFS

1. Idempotency Key as BullMQ Job ID
   → Prevents duplicate job creation. If server restarts and requeuePendingEmails()
     tries to add a job that's already in Redis, BullMQ silently ignores it.

2. Two-layer persistence (Redis + PostgreSQL)
   → Redis (BullMQ) handles the queue. PostgreSQL is the source of truth.
   → If Redis data is lost, requeuePendingEmails() rebuilds from DB.

3. Clock-aligned hour windows (not rolling)
   → hourWindow = Math.floor(Date.now() / 3600000)
   → Simpler implementation. Trade-off: a burst at xx:59 and xx:00 could
     technically send 2x the limit. Acceptable for this scope.

4. Rate-limited jobs: reschedule, don't fail
   → Jobs go back into the queue with a new delay for the next hour.
   → Status changes: SCHEDULED → RATE_LIMITED → SCHEDULED (rescheduled)

5. Elasticsearch is optional
   → If ES is down, the app still works. Search returns empty results.
   → Makes local dev easier without requiring all services.

6. JWT passed via URL after OAuth
   → After Google callback, token is in the redirect URL: /auth/callback?token=xxx
   → Frontend extracts and stores in localStorage.
   → Production should use httpOnly cookies exclusively.

7. Staggered bulk scheduling
   → Each recipient[i] gets scheduledAt + (i * delay), not all at once.
   → Naturally distributes load without needing complex queuing logic.
